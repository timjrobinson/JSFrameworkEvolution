Chapter 3 · 2013–2016

Components and the virtual DOM

React's pitch was that tracking changes is the wrong problem. Describe what the screen should look like for any given state, run that description again whenever state changes, and let the library work out the difference.

Facebook's problem in 2011 was the one from the last chapter, at scale. Its ads tools and chat had state that changed constantly from many sources, and bugs kept reappearing. The most famous was the unread-message counter that said "1" when there was nothing to read. It was fixed and came back, repeatedly, because several pieces of code each updated it by hand.

The engineer Jordan Walke noticed that Facebook's server-side code didn't have this class of bug. On the server, in PHP with an extension called XHP, you didn't update a page. You rendered it from scratch on every request, from the current data. He asked whether the client could work the same way.

React

2013 · Jordan Walke · Facebook

A React component is a function from data to a description of UI. When data changes, React calls the function again, gets a new description, compares it with the previous one, and applies only the differences to the real page. That in-memory description is the virtual DOM.

React also put the markup inside the JavaScript, using a syntax extension called JSX. This was received badly. A decade of best practice said HTML, CSS and JavaScript belonged in separate files. Pete Hunt's reply, in a talk titled "Rethinking Best Practices", was that templates and their logic were one concern, already tightly coupled, and that separating them by file type was separating technologies and not concerns.

Why
To make UI bugs caused by out-of-sync state impossible by construction.
Borrowed
XHP's components-as-markup. Functional programming's idea of UI as a pure function of state. Backbone's "just re-render it", made fast.
Reacted to
Two-way binding and template languages. In React, data flows down through props, events flow up, and loops are just .map().
Got right
Components as the unit of everything. A simple mental model that scaled to large teams. And because rendering was abstracted from the DOM, the same model drove server rendering and React Native.
Fell short
It was only the view. Routing, data fetching and state management were left to a churning ecosystem, producing the "JavaScript fatigue" of 2015–16. Re-running everything is wasteful by default, so performance work meant hand-placing shouldComponentUpdate and later useMemo. And it effectively required a build step.
Outcome
Not replaced. React became the default, and every framework since has been defined partly by how it differs from React.

Flux & Redux

2014 · Facebook  ·  2015 · Dan Abramov, Andrew Clark

React handled the view. Flux was Facebook's pattern for the data behind it: state lives in stores, changes happen only by dispatching actions, and everything flows in one direction. Dozens of implementations appeared within a year. Redux won by reducing the idea to a single store, plus pure functions called reducers that take the old state and an action and return the new state.

Borrowed
Redux took its architecture almost directly from Elm, and its name for the core function from Array.prototype.reduce.
Got right
Predictability. Every change was a logged, replayable event, which made time-travel debugging and hot reloading possible. It made immutable data mainstream in JavaScript.
Fell short
Boilerplate. Changing one field could mean touching an action type, an action creator, a reducer and a selector. It was also applied far beyond its need, to hold form inputs and server responses that were never really global state.
Outcome
Split up by purpose. Server data moved to caching libraries such as React Query and Apollo. Local state went back into components with hooks. What remained moved to lighter stores. Redux Toolkit quietly added mutable-looking syntax back on top.

Elm

2012 · Evan Czaplicki

Elm isn't a JavaScript framework. It's a separate, purely functional language that compiles to JavaScript. It belongs here because of its influence. The Elm Architecture is three parts: a model, an update function that produces a new model from a message, and a view function that renders the model.

Got right
No runtime exceptions in practice, famously helpful compiler errors, and an architecture so clean that Redux copied it wholesale.
Fell short
It asked you to leave the JavaScript ecosystem. Interop was deliberately restricted, the language was governed tightly by a very small team, and releases slowed to a near stop after 2019.
Outcome
A small, loyal community. Its ideas travelled much further than the language did.

Vue

2014 · Evan You

Evan You had used AngularJS at Google and liked the declarative templates and data binding but not the weight. Vue was his extraction of the good parts. Version 1 was, mechanically, close to Knockout: reactive data with dependency tracking, driving direct DOM updates. The difference was ergonomics. Vue used JavaScript getters and setters so reactive data looked like plain objects. Version 2, in 2016, added a virtual DOM underneath and single-file components.

Borrowed
Templates and directives from AngularJS. Reactivity from Knockout. Components and, from v2, the virtual DOM from React.
Got right
Approachability. You could add it to a page with a script tag and no build, then grow into a full toolchain. The docs were exceptional. Official routing and state libraries spared users React's choice paralysis. It grew huge without a corporate sponsor, especially in China and in the Laravel community.
Fell short
Vue 2's reactivity had well-known blind spots, such as adding a property to an object. The Options API organised code by type and not by feature, and reusing logic through mixins scaled poorly. The migration to Vue 3 was slow and split the ecosystem for a couple of years.
Outcome
Still one of the big three. Its reactivity core, rebuilt on Proxies for Vue 3, turned out to be the model the rest of the industry later converged on.

Angular (2+)

2016 · Google

In October 2014, at ng-europe, the Angular team showed Angular 2. Controllers, scopes and ng- directives were all gone, and there was no migration path. It is still the standard case study in how not to announce a new version. What shipped in 2016 was a different framework with the same name: component-based, written in TypeScript, built around RxJS streams, with change detection driven by a library called zone.js that patched every asynchronous browser API to know when something might have changed.

Reacted to
AngularJS's own dirty-checking limits, and React's component model, which it adopted.
Got right
Its bet on TypeScript, made when that was unfashionable, was vindicated across the whole industry. It remains the most complete official toolkit: router, forms, HTTP, testing and CLI, all versioned together. Large organisations value exactly that.
Fell short
The rewrite squandered AngularJS's lead. NgModules, decorators, RxJS and zones made for a heavy learning curve and large bundles. Zone-based change detection was the old dirty check with better triggers.
Outcome
Stable in the enterprise, and since 2023 steadily replacing its own foundations: standalone components instead of NgModules, and signals instead of zones.

Rob Eisenberg left the Angular 2 team in 2014 over its direction and built Aurelia, a standards-focused alternative. It was well regarded and never found a large audience.

Web Components & Polymer

2013 · Google

If components are the right abstraction, the browser should provide them. That was the bet behind Web Components: custom elements, shadow DOM for style encapsulation, and <template>. Polymer was Google's library on top, and for a while Google suggested it was the future of all web development.

Got right
Interoperability. A custom element works in any framework or none, which makes it the natural choice for design systems that must outlive framework fashions.
Fell short
Standardisation took most of a decade, and one of the four original specs, HTML Imports, was rejected by other browsers. Polymer depended on heavy polyfills in the meantime. Worse, the standards gave you an element lifecycle but no answer to the question everyone was actually asking: how do I render from state? Server rendering was also unsolved for years.
Outcome
Polymer shrank into Lit, a small and well-liked rendering library. Web Components became a solid interop layer, not the framework-killer once promised.

The small ones: Preact, Mithril, Riot

2014–2015

React's ideas were simple enough to reimplement, and a wave of libraries did so in a fraction of the size. Mithril bundled a virtual DOM, router and request helper in a few kilobytes. Riot offered custom-tag components. Preact, by Jason Miller, reproduced React's API in about 3 kB.

Got right
They proved the virtual DOM was a technique, not a product, and kept pressure on React's bundle size.
Outcome
Preact endures wherever bytes matter. It also became an idea laboratory: Miller's writing popularised islands architecture, and Preact was the first React-like library to adopt signals.

What the era settled

Components won, completely. By 2016 Angular, Vue, Ember and the web platform itself had all reorganised around them. One-way data flow became the default assumption. JSX went from heresy to ordinary.

The costs arrived together. Every serious app now needed a compiler and a bundler. The browser received an empty <div> and a megabyte of JavaScript, and nothing appeared until that JavaScript had downloaded and run. And re-running components to find what changed did a lot of work to conclude that most things hadn't. Chapter 4 is about people attacking each of those.
