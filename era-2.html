Chapter 2 · 2009–2012

Apps need structure

jQuery made it easy to change the page. It offered no opinion on where your data lived or how the page should find out it had changed. Four frameworks gave four different answers.

The typical large jQuery application of 2009 stored its state in the DOM. To find out whether a to-do item was done, you checked whether its <li> had a class of completed. To update a counter, you found every place the count was displayed and rewrote each one by hand. Forget one and the page disagreed with itself.

The fix was borrowed from server and desktop programming: keep the data in models, separate from the views that display it. This was the "MV-something" era, so called because nobody agreed on the third letter.

The interesting question was how a view learns that a model changed. Each framework below picked a different mechanism, and each mechanism reappears later in this history.

SproutCore

2007 · Charles Jolley · later Apple

SproutCore tried to bring Cocoa, Apple's desktop framework, to the browser: key-value observing, bindings, and a full widget set drawn by the framework rather than written as HTML. Apple used it to build MobileMe and the first iCloud web apps.

Got right
Bindings and computed properties that kept the UI in sync automatically. It showed that "desktop-class" apps in a browser were possible.
Fell short
It fought the web instead of using it. HTML and CSS were treated as a rendering detail, the apps were heavy, and URLs were an afterthought.
Outcome
Its 2.0 rewrite dropped the widgets, embraced HTML templates, and was renamed Ember.

Backbone.js

2010 · Jeremy Ashkenas

Backbone was the minimum viable structure: Models and Collections that fire events when they change, Views that listen and re-render, and a Router. About 1,500 lines, sitting on top of jQuery and Underscore. It was extracted from DocumentCloud, a real newsroom application.

Why
To get data out of the DOM with as little framework as possible.
Mechanism
Manual events. A model emits change; you write the code that listens and updates the page.
Got right
Small, readable, unopinionated, and it mapped neatly onto REST APIs. Trello, Airbnb, Hulu and many others shipped on it. You could read the entire source in an evening.
Fell short
It left the hard part to you. The simplest way to update a view was to re-render the whole template, which was slow and lost focus and scroll position. The efficient way was hand-written DOM surgery. Nested views leaked memory through forgotten listeners ("zombie views"). Every team built its own framework on top, and no two matched.
Outcome
Replaced by frameworks that automated the model-to-view step. But the instinct to "just re-render the whole thing" is exactly what React later made fast.

Knockout

2010 · Steve Sanderson

Knockout brought the MVVM pattern from Microsoft's WPF and Silverlight to the browser. You wrapped values in observables, derived others with computeds, and bound them to HTML with data-bind attributes. When an observable changed, exactly the DOM nodes that depended on it updated, and nothing else.

Mechanism
Fine-grained reactivity with automatic dependency tracking. Reading an observable inside a computed subscribes to it. No diffing, no re-rendering.
Got right
The reactive model itself. It was precise and efficient, and it worked back to IE6.
Fell short
The ergonomics. Every value was a function call (name() to read, name('x') to write), binding expressions lived in strings, and there was no real component or routing story. Large apps built tangled graphs of subscriptions that were hard to debug.
Outcome
Overshadowed by AngularJS, then React. But this is the single most important "loser" in the story. Twelve years later the industry rebuilt Knockout's model and called it signals.

Sanderson went on to create Blazor at Microsoft: C# components compiled to WebAssembly. The GWT idea, a third time.

AngularJS

2009–2010 · Miško Hevery, Adam Abrons · Google

AngularJS asked: what if HTML had been designed for applications? You wrote ng-repeat, ng-model and {{ name }} directly in your markup, attached plain JavaScript objects, and the framework kept the two in sync in both directions. It also brought dependency injection and a serious testing culture to front-end work. Hevery famously rewrote a 17,000-line internal Google app in about 1,500 lines of it.

Mechanism
Dirty checking. After every event, Angular re-evaluated every bound expression and compared each to its previous value, looping until nothing changed.
Got right
Productivity. A working data-bound form took minutes and almost no code. Models were plain objects. Directives were a genuine reusable-component mechanism, and the whole thing came with batteries: routing, HTTP, forms, testing.
Fell short
Performance fell off a cliff past a couple of thousand bindings on a page. Two-way binding made it hard to say why a value changed. And the concept count was brutal: scopes, the digest cycle, $apply, transclusion, and services versus factories versus providers.
Outcome
Hugely dominant through 2014. Then Google announced that Angular 2 would be incompatible, and a large share of its users left for React and Vue.

Ember.js

2011 · Yehuda Katz, Tom Dale

Ember was SproutCore 2.0 after a rethink, led by people from the Rails and jQuery core teams. Its philosophy was Rails': convention over configuration. Its central conviction was that the URL is the heart of a web app, so the router came first, with nested routes that mapped to nested templates and data loading.

Mechanism
Key-value observing. You read and wrote through get() and set() so the framework could track changes and update bound Handlebars templates.
Got right
The router, which React Router and later Remix openly descended from. Ember CLI, which established the idea that a framework should ship its own build tool and generators. And a "stability without stagnation" upgrade process that carried apps across major versions for a decade.
Fell short
A steep learning curve, a large download, and conventions that felt like a wall whenever your app didn't fit them. Its object model predated ES classes and aged badly.
Outcome
Never beaten outright. It kept its users (LinkedIn, Apple, Discourse) but stopped gaining new ones once React arrived. Much of what it pioneered is now standard in meta-frameworks.

Meteor

2012 · Meteor Development Group

Meteor's demo was astonishing in 2012. One JavaScript codebase ran on client and server. You queried the database from browser code. Change a record and every connected browser updated live. Deploy with one command.

Got right
The vision. Isomorphic code, optimistic UI, live queries, a zero-config build, and calling server functions from the client as if they were local.
Fell short
It was a closed world: its own package manager instead of npm, MongoDB only, its own view layer, and real-time by default even where that didn't scale. When React and npm won, Meteor was on the wrong side of both.
Outcome
The company pivoted to GraphQL and became Apollo. But look at what server actions offer in 2024 and compare it with that 2012 demo.

What the era settled

It settled that data should live in JavaScript and the DOM should be a projection of it. It did not settle how to keep them in sync. In 2012 you could choose manual events, observables, dirty checking, or key-value observing, and each had a serious flaw.

There was also a growing unease about templates. Every framework here had invented its own small language inside HTML strings or attributes, each with its own rules for loops, conditions and scope. In 2013 a team at Facebook proposed throwing all of that out. That's chapter 3.
