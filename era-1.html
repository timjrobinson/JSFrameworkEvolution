Chapter 1 · 1995–2008

Taming the browser

The first generation of libraries wasn't trying to structure applications. It was trying to make the same line of code work in Internet Explorer 6 and Firefox.

For its first decade JavaScript was a toy: form validation, image rollovers, and "DHTML" snowflakes that followed your cursor. Pages came from the server, fully formed. If you wanted new data, you clicked a link and got a new page.

Two things changed that. In 1999 Microsoft shipped XMLHTTP in Internet Explorer 5 so that Outlook Web Access could fetch mail without reloading. Then in 2004 and 2005, Gmail and Google Maps showed what the technique could do, and Jesse James Garrett gave it a name: Ajax.

Suddenly everyone wanted to write real programs in the browser, and discovered the browser was a terrible place to write programs. Event handling differed between IE and everyone else. So did Ajax, so did the box model, so did how you found an element. The language had no modules and a standard library you could fit on a postcard.

The libraries of this era all solved that same problem. They differed on how much to solve, and on whether to fix JavaScript itself or to wrap it.

Dojo Toolkit

2004 · Alex Russell, Dylan Schiemann, David Schontzler

Dojo was the first library to treat the browser as a serious application platform. It had a module system and loader years before the language did, a full widget set (Dijit), a build tool, internationalisation, and Deferred objects for asynchronous code.

Why
To pool the DHTML tricks several teams had each built in private into one professional-grade toolkit.
Borrowed
Deferreds from Python's Twisted, by way of MochiKit. Packages and widgets from desktop UI toolkits.
Got right
Almost everything, early. Dojo's module loader fed directly into AMD and RequireJS. Its deferreds became jQuery's, then Promises/A+, then the Promise in the language.
Fell short
It was big, the documentation was thin, and it took a week to learn when jQuery took an afternoon. Enterprises adopted it; the wider web didn't.
Outcome
Never beaten on features, only on approachability. A lesson later frameworks relearned repeatedly.

Prototype & script.aculo.us

2005 · Sam Stephenson, Thomas Fuchs

Prototype came out of the Ruby on Rails world, and its goal was to make JavaScript feel like Ruby. It added each, map and bind to the built-in objects, gave the world the $() function, and wrapped Ajax in one tidy call. Its companion script.aculo.us added the animations that defined the "Web 2.0" look.

Why
Rails wanted Ajax helpers, and raw cross-browser JavaScript was miserable.
Borrowed
Ruby's Enumerable, class-based inheritance, and general taste.
Got right
The language improvements. Function.prototype.bind, Array.prototype.forEach and friends are in JavaScript today partly because Prototype proved people wanted them.
Fell short
It did this by modifying built-in prototypes and DOM elements directly. That collided with other scripts, with browser quirks (IE didn't expose element prototypes at all), and eventually with the standards process.
Outcome
Rails switched its default to jQuery in 2011. "Don't modify objects you don't own" became a rule of the language.

jQuery

2006 · John Resig

jQuery had one idea and executed it perfectly: find elements with a CSS selector, then do something to all of them. $('.item').hide(). It wrapped elements instead of modifying them, so it coexisted with anything. Every method returned the collection, so calls chained. And it had a plugin system simple enough that thousands of people wrote one.

Why
Resig found Prototype's approach invasive and the DOM API unbearably verbose. He wanted the common cases to be one line.
Borrowed
CSS-selector querying from Dean Edwards' cssQuery and Simon Willison's getElementsBySelector. The $ from Prototype.
Got right
Developer experience, before anyone called it that. Excellent docs, a tiny concept count, and browser bugs that simply vanished. At its peak it ran on most of the web's sites, and it's still on a majority of them.
Fell short
It was a tool for changing pages, not building applications. There was no place to keep state except the DOM itself, so large jQuery apps became webs of event handlers reading values back out of the HTML they'd just written.
Outcome
Killed by success. Browsers shipped querySelectorAll, classList, fetch and CSS transitions, each a standardised piece of jQuery. Once IE died, nothing was left to paper over.

MooTools

2006 · Valerio Proietti

MooTools was Prototype's ideas with more polish: a proper class system, a modular build, and very smooth animation. For a while "jQuery or MooTools?" was a real argument, summed up as "jQuery is for the DOM, MooTools is for JavaScript".

Got right
Classes with mixins, years before the language had class. Code written in MooTools tended to be better organised than the jQuery equivalent.
Fell short
It extended native prototypes, as Prototype did. So many old sites still carry it that TC39 has twice had to rename new language features to avoid breaking them: Array.prototype.contains became includes, and flatten became flat.
Outcome
Faded as jQuery's plugin ecosystem pulled ahead. Its lasting influence on JavaScript is, awkwardly, in the names the language couldn't use.

YUI & Ext JS

2006 · Yahoo · Jack Slocum

The Yahoo User Interface library was the corporate answer: carefully namespaced, exhaustively tested across a published browser-support grid, and complete with widgets. Ext JS began as an extension to YUI and grew into a commercial toolkit for building desktop-style admin screens.

Got right
Engineering discipline. YUI gave the industry graded browser support, CSS resets and grids, a minifier, and the first widely used performance guidance. YUI 3's module loader was ahead of its time.
Fell short
Verbose (YAHOO.util.Dom.getElementsByClassName), and maintained by one company whose fortunes were declining.
Outcome
Yahoo ended development in 2014, citing the shift to Node, npm and the new application frameworks. Ext JS survives in enterprise software.

Google Web Toolkit

2006 · Google

GWT took the most radical position of the era: JavaScript is too poor a language to write applications in, so don't. Write Java, with types and an IDE, and compile it to JavaScript, generating a separate optimised bundle per browser.

Why
Google had large teams of Java engineers and large applications to build.
Got right
The diagnosis. Static types, dead-code elimination, code splitting, and treating JavaScript as a compile target are all standard practice now.
Fell short
The cure. Slow compiles, opaque output, awkward interop with ordinary JavaScript libraries, and a UI model borrowed from Swing.
Outcome
Google moved on to Closure, Dart and then TypeScript. But "the framework is a compiler" would come back ten years later, and win.

What the era settled

By 2008 the browser-compatibility problem was, in practice, solved, and jQuery was the answer. The losing libraries were not worse engineered. Dojo and YUI were more complete; MooTools was arguably more elegant. They lost because jQuery asked for less: less to learn, less to commit to, less to load.

What nobody had solved was the next problem. Web apps were getting bigger, and a library for poking at the DOM gave no help in deciding where the data should live. That is where chapter 2 starts.
