Chapter 4 · 2016–2020

Compilers and meta-frameworks

Once every project had a build step anyway, two questions followed. How much of the framework could the build step do in advance? And could it also render the page on the server, so the user wasn't staring at a blank screen?

The single-page app of 2016 had a characteristic failure. The server sent an almost empty HTML file. The browser downloaded a large bundle, parsed it, ran it, fetched data, and only then drew anything. On a fast laptop this was fine. On a mid-range phone on a mobile network it could take ten seconds. Search engines and link previews often saw nothing at all.

Two separate movements grew out of that. One pushed work from the browser into the compiler. The other pushed rendering from the browser back to the server. They would merge in the next chapter.

Next.js, Nuxt & Gatsby

2016 · Guillermo Rauch / Zeit  ·  Sébastien & Alexandre Chopin  ·  Kyle Mathews

React could render to an HTML string on a server from early on. Wiring that up yourself, with routing, data fetching, code splitting and a bundler config, was a project in itself. Next.js packaged it. Put a file in pages/ and it became a route, rendered on the server, then "hydrated" in the browser so React could take over. Nuxt did the same for Vue weeks later. Gatsby did it at build time, producing static files.

Why
To fix the blank-page problem and end the per-project webpack configuration ritual.
Borrowed
File-system routing straight from PHP, as the Next.js announcement said outright. Batteries-included conventions from Ember and Rails.
Got right
They made the view library into a full framework and settled the "which router, which bundler" exhaustion. The meta-framework became the normal way to start a project. By 2023 React's own docs recommended starting with one.
Fell short
Hydration. The server renders the page, then the browser downloads all the same components and runs them all again just to attach event handlers. The user pays for the page twice, and it looks ready before it responds. Gatsby had a further problem: its mandatory GraphQL data layer made builds slow and the learning curve steep. It faded after 2020 and was absorbed by Netlify in 2023.
Outcome
Next.js became the default React setup. The hydration cost it normalised became the central problem of the next era.

Svelte

2016 · Rich Harris

Rich Harris was a graphics editor at the Guardian, building interactive articles that had to load fast on phones. His earlier library, Ractive, was a conventional runtime. Svelte's premise was that the framework shouldn't be in the browser at all. A Svelte component is compiled, at build time, into plain JavaScript that updates precisely the DOM nodes it needs to. No virtual DOM, no diffing, very little runtime.

Svelte 3, in 2019, pushed further. Reactivity became a language feature: assign to a variable with count += 1 and the compiler works out what to update.

Reacted to
The virtual DOM, which Harris called "pure overhead": work done at runtime to discover what a compiler could have known beforehand.
Borrowed
Single-file components from Vue and Ractive. The compile-it-away stance from GWT's lineage, though with a far lighter touch.
Got right
Tiny output, strong performance, and the least code per component of any mainstream framework. It consistently topped developer-satisfaction surveys. It made "compiler" a normal word in framework design.
Fell short
Compile-time reactivity only worked at the top level of a .svelte file. Move logic into a plain .js module and it stopped being reactive, so you needed a second system (stores) for shared state. The rules around $: statements had surprising edge cases. The ecosystem stayed small beside React's.
Outcome
Svelte fixed these in 2024 by replacing its own model with runes, which are signals with compiler help.

React Hooks

2019 · Sebastian Markbåge, Sophie Alpert, Dan Abramov

Not a new framework, but a change large enough to count as one. Until 2019, React components with state were classes. Sharing stateful logic between them needed awkward patterns, and related code was scattered across lifecycle methods. Hooks let plain functions hold state with useState and run side effects with useEffect, and let you package both into reusable custom hooks.

Got right
Composition. Custom hooks were a far better unit of reuse than mixins, higher-order components or render props. The whole industry followed: Vue's Composition API was a direct response.
Fell short
Hooks made React's central inefficiency the developer's job. Because the whole function re-runs on every render, you must tell React what each effect depends on, by hand, in an array. Get it wrong and you have stale values or infinite loops. Performance means wrapping things in useMemo and useCallback. And useEffect became the default home for data fetching, which it was never well suited to.
Outcome
The dependency array is the most persuasive advertisement signals ever had. Systems with automatic dependency tracking simply don't need one.

Solid

2018 · Ryan Carniato

Ryan Carniato had been a happy Knockout user and didn't believe the virtual DOM was a necessary cost. Solid looks like React: JSX, components, and a createSignal that resembles useState. It works like Knockout. A component function runs once. The compiler turns JSX into real DOM nodes wired directly to signals, so when a signal changes, only the specific text node or attribute bound to it updates.

Borrowed
Fine-grained reactivity from Knockout and Adam Haile's S.js. JSX and one-way data flow from React. Compilation from Svelte.
Got right
It showed you could keep React's authoring model and drop its runtime cost, with benchmark results near hand-written DOM code. No dependency arrays and no memoisation.
Fell short
It looks like React and isn't, so React habits such as destructuring props silently break reactivity. Its ecosystem and job market are small.
Outcome
Modest adoption, enormous influence. Carniato's writing and benchmarks did more than anything else to bring signals back, and nearly every major framework has since adopted Solid's core design.

The tooling underneath: webpack to Vite

2012–2020

None of this era was possible without build tools, and they have their own lineage. Browserify (2011) let browser code use Node-style modules. webpack (2012) bundled everything, including CSS and images, and enabled code splitting, at the price of famously intricate configuration. Babel (2014) let people write next year's JavaScript, and JSX, today. Rollup (2015), also by Rich Harris, introduced tree shaking.

Fell short
By 2019 a large app's dev server could take a minute to start, because it bundled everything before serving anything.
Outcome
Vite, from Vue's Evan You in 2020, served source files as native ES modules and transformed them on request with compilers written in Go and later Rust. Startup became near-instant. Within three years almost every framework except Next.js had standardised on it, a rare case of the ecosystem agreeing on something.

Native modules in the browser, no bundle in development: this is roughly how people loaded scripts in 2008, with one tag per file. The difference is that it now works.

What the era settled

A framework is no longer just a library you load. It is a compiler, a dev server, a router, and a server runtime. The questions shifted accordingly, from "how do I update the DOM efficiently?" to "what should run where, and when?"

And the price of the answer so far, hydration, was now obvious to everyone. The site rendered on the server and then did it all again in the browser. Chapter 5 covers the attempts to stop paying twice.
